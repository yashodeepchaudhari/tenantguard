The 3 Planes

PlaneComponentsJob
Datagateway, w0..w8, spare, quarantineServe every tenant request: identify, admit, queue fairly, route by barcode, measure
ControlbrainWatch telemetry + worker stats; rescue victims, name the culprit, prove it by relocation, give a verdict, throttle with TTLs, charge background CPU, explain every action
Managementadmin API, UI, handoff bridge, billing, narrator, lab, demo driverOperators see and steer it: modes, quotas, cases, attacks, scorecard, fair bills, incident reports

The 5 Layers of Isolation (not just a rate limit)

LayerNameWhat it doesWhere
L1RequestIdentity, token bucket, retry budget: a flood or retry storm gets 429 with an accurate Retry-Aftergateway/admission.py, retry.py
L2CostA CPU-ms bucket debited with the CPU each request really used (measured by the worker)gateway/buckets.py
L3SchedulerWeighted DRR in 3 lanes behind an adaptive per-worker window: cheap requests never wait behind a whalegateway/scheduler.py, limiter.py
L4Kernelcgroup CPU / memory / pids limits per worker container; spare and quarantine poolsdocker-compose.yml
L5DataOne SQLite file per tenant; namespaced cache with a guaranteed share; per-tenant memory budgetworker/app/store.py, cache.py
+ Adaptive loopThe brain: rescue, name, prove, judge, throttle, recover. It works even when the harm is invisible to L1 and L2.

Adaptive Throttling Ladder (Stage 2)

LevelEnters whenAction (always with a TTL)
normal-Full plan
warnnoisy score ≥ 1.5, use ≥ 1.6× fair share and ≥ 4 neighbours hurt, held 5 sIncident opened, nothing throttled
throttlescore ≥ 2.0, held 2 sQuota × 0.5 per step (AIMD), via LimitsCmd
deprioritizestill noisy, held 4 sScheduler weight × 0.25
quarantinescore ≥ 4.0, held 6 sQuota × 0.1 and weight × 0.1; a block needs human approval (handoff case)
recoverscore < 1.0, held 10 s+0.1 factor per step back to the full plan

Thresholds and hold times come from tenantguard.yaml (brain.noisy). Rescue comes first: the ladder acts only if harm persists. A legit burst that hurts nobody is never throttled.

Stage 3: Rescue, Name, Prove

StepHow
HealthEach server's p95 compared with its peers (median over its tenants, so a whale's own slow requests don't count). Calibrated on the Docker host: the signal must be sustained over a 5 s window, and a server is never "slow" below 25 ms or half the strictest SLA on it
RescueRoute weights move victims off slow servers onto their healthy ones, keeping every server under 70% CPU
NameAG(2,3) barcodes: any two tenants share at most one server, so the set of slow servers decodes to the culprit (with a confidence) or to a host fault with no tenant blamed. A slow server where a hot tenant runs is held: that tenant is judged before the server is suspected
ProveMove the suspect to the spare: the original servers recover and the slowdown follows it (R = 1 − post/pre slowdown). DockerProver sizes the spare through the Docker socket; a suspect host is drained and measured idle
Verdictmitigated_no_blame (not proven: nobody penalised) · over_plan (the ladder tightens limits) · costly_pattern (only the class that grew goes to quarantine) · honest_growth (keeps the spare as a burst lane, no penalty) · host_fault (host stays drained). TTL-bound, limited by an action budget

Safety

RuleHow
Auto-undoEvery control override has a finite TTL (≤ gateway.ttl_max_s) and reverts by itself; the brain renews it while needed
Fail-staticIf brain heartbeats stop for 2 s, the gateway keeps its last config while TTLs still expire. A dead brain never leaves a tenant punished
Humans and ladder agreeOperator release / extend go to the brain (OperatorCmd), so the ladder obeys them instead of fighting them
Hardened edgesControl token on /admin/*, /control/*; path guard (no traversal to worker admin); bounded TTLs and quotas; capped request bodies

Version 2: Simple Project Flow (Team View)

The Big Picture in One Line

  Tenants ──► GATEWAY (who are you? within your plan? fair turn?) ──► WORKERS (do the work, meter it)
                 ▲                                                        │
                 │ throttle / reroute / block, always with a timer        │ how slow, how much CPU, whose
                 └───────────────────────── BRAIN ◄───────────────────────┘
                                              │
                                              └──► DASHBOARD + on-call case ("who did it, what we did, why")

A Request's Journey, Step by Step

  1. Tenant K sends  POST /api/ingest  with its API key
   │
  2. Gateway: "You are K (Pro plan)." Unknown key? → 401
   │
  3. Within your plan?  rate ✓  CPU budget ✓  in-flight ✓  not a retry storm ✓   (else 429 + "retry in 2 s")
   │
  4. Wait your fair turn: cheap requests take the express lane; nobody waits more than 1 s (else 503)
   │
  5. Go to one of K's 3 servers (its "barcode"), avoiding slow or drained ones
   │
  6. Worker does the work in K's own database and charges the CPU to K
   │   ...but the black-box indexer it triggers burns 300× more CPU that nobody bills
   │
  7. Gateway records the latency for (K, server) and reports it to the brain every 250 ms

The Automatic Protection Loop (4 times a second)

   ┌────────────────────────────┐
   │ 1. WATCH                   │  Which servers are slower than their peers? Who uses more than a fair share?
   └─────────────┬──────────────┘
                 ▼
   ┌────────────────────────────┐
   │ 2. RESCUE  (about 1 s)     │  Move the innocent tenants to their healthy servers
   └─────────────┬──────────────┘
                 ▼
   ┌────────────────────────────┐
   │ 3. NAME                    │  The slow servers form a pattern; only one tenant's barcode fits it
   └─────────────┬──────────────┘
                 ▼
   ┌────────────────────────────┐
   │ 4. PROVE + JUDGE           │  Move the suspect to the spare: does the slowdown follow it? Then a verdict
   └─────────────┬──────────────┘
                 ▼
   ┌────────────────────────────┐
   │ 5. ACT  (with a timer)     │  warn → throttle → lower priority → quarantine; a block needs a human OK
   └─────────────┬──────────────┘
                 ▼
   ┌────────────────────────────┐
   │ 6. RECOVER                 │  Behaving again? Give back its plan step by step; timers undo everything
   └─────────────┬──────────────┘
                 └──────► repeat, and explain every step on the dashboard and in the on-call case

Which Box Does What

BoxIn one sentence
GatewayThe front door: knows every tenant, enforces its plan, keeps the queue fair, and obeys the brain's timed orders.
WorkersThe shared app: does the work, keeps each tenant's data apart, and measures exactly what each tenant costs.
BrainThe detective: spots slow servers, rescues victims, names the culprit, proves it, decides the verdict, and turns the throttle up or down.
DashboardThe control room: every tenant, every server, every incident and the reason for every action, live.
LabThe crowd: 12 realistic tenants plus attacks, and the measured scorecard.
Handoff bridgeTurns each incident into a case for the on-call engineer and carries their decision back.
BillingBills each tenant fairly: victims never pay for contention, SLA misses earn credits, and each tenant can ask "Why was I slow?".
NarratorWrites the incident report and a customer message that names nobody.
